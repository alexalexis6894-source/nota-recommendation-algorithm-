# Заявки и проверка состава через двух ботов

`@alannotabot` — управление заявками; `@notaadmin1bot` — проверка состава поставщиком.
Токены, пароли и клиентские данные в Git не добавлять. Фактическое подключение требует
доступа к серверу с рабочей `data/photos.sqlite` и запуска обоих обработчиков.
Копия репозитория сама по себе не подключается к заказам рабочего сайта.

## Работа с заявкой

1. Новая заявка с сайта поступает в чат менеджера. Старую можно открыть `/order 123`.
2. **Оплатил** отмечает полученную оплату сразу, без обязательного согласования.
   Это ручная отметка, деньги бот не списывает. Дата оплаты сохраняется при следующих сменах статуса.
3. **Проверить состав** ставит состав в очередь поставщику. Повторное нажатие не дублирует проверку.
4. Поставщик получает бренды, названия и объёмы, нажимает **OK, состав подтверждаю**
   или **Нужны изменения**. Менеджер получает карточку с результатом и сам отмечает оплату.
   Ответ поставщика не отмечает оплату автоматически.
5. До оплаты менеджер может заменить позицию: `/replace 123 2 9828` — в заявке 123
   заменить вторую позицию ароматом с PID 9828 из серверного каталога.
   Объём и цену берём из `offers.json`, сумму и бонусы пересчитываем.
   PID — идентификатор Фрагрантики в каталоге. `/order 123` показывает обновлённую карточку.
6. Любая замена отменяет прежнее подтверждение: нажмите **Проверить состав** ещё раз.
   Старые кнопки поставщика не могут подтвердить изменённый заказ.
   Оплаченные и закрытые заявки заменой не редактируются.

Обычное текстовое «OK» не изменяет заказ: поставщик нажимает кнопку у нужной заявки,
чтобы не перепутать несколько одновременно обсуждаемых составов.

## Установка на существующий сервер

1. Сделать резервную копию рабочей `data/photos.sqlite` штатным SQLite backup API.
   Опубликовать `app/telegram.py`, `app/supplier.py`, `app/orders.py`, `telegram_poll.py`
   и обновлённый `passenger_wsgi.py` в существующий каталог бэкенда. Не подменять
   рабочую базу и каталог данными из Git. Если параллельно идёт перенос в облако,
   применить изменения к актуальной версии приложения на целевом сервере.
2. Создать конфиги по `backend/telegram.json.example` и
   `backend/supplier-telegram.json.example` **вне публичного каталога**.
   Задать разные случайные `pairing_code` и `webhook_secret` для двух ролей,
   например через `secrets.token_urlsafe(24)`. Установить права `600`.
   Переменные окружения: `NOTA_TELEGRAM_CONFIG` и `NOTA_SUPPLIER_TELEGRAM_CONFIG`.
   По умолчанию `passenger_wsgi.py` и `telegram_poll.py` ищут файлы рядом с собой.
3. На REG.RU добавить второй cron рядом с существующим менеджерским опросом:

   ```cron
   * * * * * /PATH/venv/bin/python /PATH/backend/telegram_poll.py --role manager
   * * * * * /PATH/venv/bin/python /PATH/backend/telegram_poll.py --role supplier
   ```

   Для менеджера сохранён существующий путь блокировки `telegram-poll.lock`;
   существующий cron нужно заменить, а не добавлять второй опрос того же бота.
   У ролей независимые offset, дедупликация обновлений, блокировки и привязки чатов.
   Опрос раз в минуту работает до 55 секунд; обычно доставка занимает до 10–15 секунд,
   на границе запусков возможна дополнительная пауза.
4. Менеджер отправляет `/start <manager pairing_code>` в `@alannotabot`,
   поставщик — `/start <supplier pairing_code>` в `@notaadmin1bot`.
   Можно использовать личные чаты или рабочие группы. Код роли даёт доступ к её заявкам,
   поэтому передавать его только нужным участникам.
   Для заранее известных чатов заполнить `chat_ids` и `allowed_user_ids`:
   первое разрешает доставку, второе — действия пользователя. Пользователь должен
   сначала открыть чат с ботом; бот не может начать личную переписку сам.
5. Проверить на тестовой заявке: прямую отметку оплаты; согласование → OK → оплату;
   отказ → замену позиции → новое согласование. Проверить также отказ чужому пользователю.

На облачном сервере можно оставить те же два cron либо настроить вебхуки
`POST /v1/telegram/webhook/manager` и `POST /v1/telegram/webhook/supplier`.
Для каждого задать свой `secret_token` в Telegram; он должен совпадать с
`webhook_secret` в конфиге. Старый `/v1/telegram/webhook` остаётся менеджерским.
Не запускать getUpdates и вебхук одного бота одновременно: опрос автоматически снимает
мешающий вебхук без очистки очереди. При использовании только вебхуков всё равно нужен
фоновый запуск `retry_pending` и `supplier.deliver_pending` для новых заказов с сайта
и повторов после сетевых ошибок: сам сайт не вызывает Telegram.

## Проверки и ограничения

```sh
python -m unittest discover -s backend/tests -v
```

SQLite-миграции добавляют `paid_at` и таблицы проверок, не удаляя существующие заявки.
Старые update ID и offset менеджера сохраняются. Успешные доставки учитываются
отдельно для каждого чата. При сетевой ошибке повтор возможен спустя 60 секунд.
Как у любого Bot API outbox, если Telegram принял сообщение, а соединение оборвалось
до получения ответа, при повторе возможно дублирующее сообщение; повторное решение
по одной проверке не применяется.

Сайт поставщика и автоматическое размещение заказа на нём не участвуют в этом сценарии:
поставщик вручную подтверждает наличие через Telegram. Цены замены берутся из
существующего серверного каталога предложений.
